# タスクカタログ v7

[English](README.md) · [72操作の定義](TASKS.md) · [185 subsetの調査対応表](finevision_mapping_185.md)

専門タスクの環境・校正と研究用CLIは[専門検証と研究実験](specialist-and-research_ja.md)を参照してください。

カタログを **65の標準候補＋7の条件付き拡張、合計72タスク・14ファミリー**へ再編しました。対応表は185 subset・527タスク句の調査記録です。画像の正解や学習レコードとしては扱わず、モデル入力にも渡しません。

## 定義済みタスクと実行可能なタスク

`pixelogue compile` は全定義、厳密なJSON Schema、旧24 IDの参考移行表に加えて `task_admission` を出力します。各タスクの必要な検証器と、通常プロファイルを実行できない具体的な理由を確認できます。

**標準65操作すべて**に通常検証経路を接続しました。追加した31操作は、回答を見せない2回の構造抽出の後、有限集合・算術・表・チャート・文書・数式・グラフ・目盛り・明示された幾何条件・有限パターンを計算で照合します。未対応記法、抽出不足、解の曖昧さ、抽出結果の不一致は棄権します。`grounded_arithmetic` も同じ厳密な数値基盤へ接続し、従来の加減乗除を回帰確認します。精度と単位は公開条件に従います。

専門拡張7操作の初版検証器を実装し、`tasks.enabled_extensions` に指定できます。通常選択には、対象モデルと検証器版に一致する校正、実行環境、画像ごとの適格性が必要です。7操作をすべて指定した例は `configs/specialist-pilot.yaml` です。このホストでは隔離レンダラーのOS機能が使えないため、コード復元2操作は環境不足として除外されます。静的SVG・限定TikZ・HTML/CSSは隔離が使える場合だけ描画し、UI操作は指定を検査するだけで実行しません。

## 画像ごとの処理

1. 実際に渡す画像view上の領域を限定して観察します。capabilityごとに領域、根拠ID、`MET`・`NOT_MET`・`UNKNOWN`を記録し、未観察は不明として扱います。別領域のcapabilityを混ぜません。
2. 領域の根拠と検証器の有無で操作候補を絞ります。実行可能なファミリーを決定的に巡回し、その中の操作を分散します。候補上限の既定値は8です。
3. 対象、公開パラメータ、実行条件を具体化します。通常プロファイルでは全条件の `MET` が必要です。画像や履歴に由来するパラメータは同じ領域の根拠IDか確定済み公開メッセージを参照します。出力の判定ラベル一覧や固定方針を「望ましい回答」としてパラメータに渡しません。
4. 未対応のパラメータ、同じ操作の重複、回答予算超過を選択器の呼び出し前に除外します。重複判定にはカタログ版、画像、領域、プロファイル、正規化した公開条件を使い、往復番号や質問の言い換えだけでは別候補になりません。
5. 設定された選択器には画像、確定済み公開履歴、必要な操作条件だけを渡します。非公開の観察判定、出典名、注釈、他の評価器の判定は渡しません。
6. 1つの操作を実現する質問を生成し、回答生成前に両評価器が質問・公開条件・領域の適合性を独立して確認します。独立した複合要求は最初のタスクとして分類せず拒否します。明示的な複数subtaskを生成するインターフェースは未実装です。
7. holistic方式では操作条件を添えた2回の総合評価を行います。holistic・detailedの両方式で、宣言された追加検証も必須です。構造化された操作では回答を見せずに画像を2回抽出してから回答を解析し、集合・算術・Schema・接続関係をcontrollerが照合します。根拠は非公開で保存します。

2往復目という理由だけで履歴依存とは扱いません。公開要求による再分類には新しい画像事実は必須ではありません。既定の `normal` は通常のcapabilityを要求します。明示的に指定した `limitation` は局所的な対象と関連capabilityの欠落・不確実性を必要とし、その制約を独立して検証します。`false_premise` は保守的に閉じた範囲も要求し、局所的な矛盾を独立して確認します。「見つからない」だけで不在とは判断しません。意図的に回答不能な質問へ、通常用の転写・計数検証をそのまま適用しません。

## 設定と予算

```yaml
tasks:
  catalog_version: "7.0"
  candidate_limit: 8
  max_scopes: 4
  max_observations_per_scope: 20
  evidence_max_tokens: 4096
  binding_max_tokens: 4096
  answer_max_tokens: 1024
  profiles: [normal]
  enabled_extensions: []
```

領域数と観察数は運用上の上限で、50個すべてのcapabilityを列挙させる設定ではありません。最初の領域観察に続き、候補を限定して条件を具体化します。密なページは公開文で範囲を絞る、確認した大きい予算を設定する、または候補から除外します。トークン上限で終了した公開質問・回答は、JSONの括弧を補えても拒否します。構造が正しいことや2モデルの一致だけでは、視覚的な正しさは保証できません。
各候補では必須チェックID、許可する公開パラメータ名、必須の公開パラメータ名を別々に提示します。チェックがMETでも必須の選択値が欠けたbindingは契約違反として上限内で再試行し、controllerが自動補完することはありません。

証拠抽出の応答Schemaには、入力で許可したcapability名だけを列挙し、各領域で同じキーを1回だけ使える形にします。重複JSONキーは引き続き厳格に拒否し、欠けた観察は不明として扱います。既出質問と、物体同定で対象名を先に明かした質問には、質問評価の前に具体的な修正指示を返して上限内で再試行します。物体同定と場面分類では、答えになる対象ラベルと自由記述の領域説明をモデル向けの操作条件から除外します。場面分類の質問には異なる公開選択肢を2つ以上含めます。回答評価の前に、質問文や同一領域の履歴にある短い物体名（数量語・区切り文字・単複数の単純な違いを含む）、質問文で引用済みの転写結果、質問文または同一領域の履歴に既出の動作を棄却します。最低ターン数と視覚品質ゲートは維持します。
静止画の動作に関する質問では、ブレがないことだけを「静止している」根拠とはみなしません。

## 移行と集計

**新しいrun IDを使ってください。** 実行識別に設定、コード、プロンプト、Schema、カタログ、専門環境のロック、モデル・processorの版、seed、入力と権利manifestを含めます。旧24タスクの保存済みラベルは変更しません。`task_catalog_legacy.yaml` と `legacy_24_migration.json` は参考対応表です。例えば `chart_lookup` は実際の要求から再分類する必要があり、自動で2つの新操作へ割り当てません。旧storeの `replay` とバックアップは引き続き利用できます。

生成・再評価は `.operations.json` へ全確定操作と対話の最後の確定操作を集計します。失敗した後半は含めません。v7の選抜では最後の確定ファミリーを主分類とし、意味的な識別には全操作列を残します。exportの操作ID・カタログ版はprovenanceへ記録し、学習メッセージへ内部情報を入れません。検証用出典の除外と利用条件の検査も引き続き適用します。

選抜設定例は新しいファミリー名へ更新しました。小さいquotaは制約の例です。ファミリー巡回も実測済みの最適配分ではありません。本番quotaは入力画像と実際の採用状況から決め、自然写真だけで文書や図の網羅性を保証しないでください。

## 確認範囲

CPUテストは共通契約、各構造化操作のfixture、Schema・参照の拒否、領域分離、パラメータの出典、出力上限、ファミリー巡回、移行時の識別、情報境界を確認します。`pixelogue task-status --junit artifacts/cpu-junit.xml` で共有fixtureの実行状況をタスク別に記録できますが、自然画像での精度を証明するものではありません。専門校正、評価者の誤り、言語間の品質、費用、学習効果は外部評価が必要です。既存のlive rubric検査も元の少数事例を対象とします。
