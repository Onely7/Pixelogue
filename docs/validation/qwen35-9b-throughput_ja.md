# Qwen3.5-9B 処理速度の検証結果

Pixelogueで同じ8画像を処理し、1 workerと4 workersを1枚のGPU上で比較しました。4画像を並行して処理すると、最初のモデル応答から最後の応答までの測定区間は745秒から296秒へ短縮されました。速度は2.52倍、時間の削減率は60.3%です。この結果から、小規模な動作確認では画像単位の有界並列化が有効だと判断できます。ただし、本来のQwen3.8-27BとGemma 4 31Bを使ったstandard構成の性能を示す結果ではありません。

## 実験の進捗

2つの比較runは、2026年9月15日に完了しました。各runには8件の最終対話が保存されています。その後に再生検証を行っても、両方のrun storeで整合性を確認できました。進捗を再確認した時点では、Pixelogueのモデルサーバーと合成処理は動いておらず、tmuxには操作用の待機中シェルだけが残っていました。

この実験で測定した実装は、コミット `749ff15` で導入しました。

- `runtime.max_concurrent_images` 件まで、互いに独立した画像を同時に処理する。
- 1つの対話内では、前の往復に依存する順序を維持する。
- worker数を超える大量の未完了処理を一度に作らない。
- 完了した対話は入力順で返す。
- SQLiteとアーティファクトの更新だけを短時間ずつ直列化し、モデルへのHTTP要求中はrun storeのlockを保持しない。
- モデル呼び出しごとのHTTP所要時間を保存する。
- `pixelogue profile` でstage別、モデル別の呼び出し数、token数、所要時間を集計する。

複数の独立した要求をvLLMへ同時に送り、複数の要求をまとめて処理するcontinuous batchingを働かせることが目的です。worker数を変えても、生成と評価の入出力条件、修復回数、採用条件は変わりません。

## 実行条件

| 項目 | 値 |
|---|---|
| 入力 | 両runで同じ検証専用の手続き生成画像8件 |
| 設定ハッシュ | `3d43f3295a9d2c984ed32a6e9437c87724050f7e3df12955126ff74082c77e93` |
| 指示選択器 | `Qwen/Qwen3.5-2B` |
| 生成器と2つの論理的な評価器 | 1つの共有推論先で動く `Qwen/Qwen3.5-9B` |
| GPU | NVIDIA RTX 6000 Ada Generation 1枚 |
| 重み | BF16、量子化なし |
| 直列run | `qwen35-9b-perf-serial-8-20260915`、`--workers 1` |
| 並列run | `qwen35-9b-perf-parallel-8-20260915`、`--workers 4` |
| 時間の測定元 | 応答アーティファクトの保存時刻とHTTP所要時間 |

モデルサーバーの起動は完了した状態で測定しました。主とする745秒と296秒は、最初の応答アーティファクトから最後の応答アーティファクトまでの時間です。モデルの取得と読み込み、fixtureの作成、サーバー起動は含みません。評価器AとBには別々の要求を送りましたが、どちらも同じQwen3.5-9Bの重みを使用しています。確認できるのはパイプラインの実行と要求の並べ方であり、異なるモデル系列による評価ではありません。

Pixelogueの予算台帳は実際のHTTP試行をすべて数えます。一方、`model_call` テーブルは、モデルの固定情報、処理段階、要求ハッシュが同じ試行を1行にまとめます。そのため、`profile` は完了した一意な呼び出しを528回と529回と数え、並列runの終了を286秒としました。実際には、同じ要求の応答がその10秒後にも保存されています。この文書では、すべての応答を含む296秒を主結果とします。`profile` から得た2.60倍という値は、処理段階ごとの記録を比べる参考値です。

## 測定結果

| 測定値 | 1 worker | 4 workers |
|---|---:|---:|
| すべての応答を含む測定区間 | 745秒 | 296秒 |
| 相対速度 | 1.00倍 | 2.52倍 |
| HTTP応答アーティファクト | 550個 | 544個 |
| 1分あたりのHTTP応答 | 44.30回 | 110.27回 |
| 1分あたりの画像 | 0.64件 | 1.62件 |
| 1画像あたりの測定時間 | 93.1秒 | 37.0秒 |
| 全応答の入力token | 309,011 | 308,216 |
| 全応答の出力token | 37,947 | 37,940 |
| プロファイルに残った完了呼び出し | 528回 | 529回 |
| プロファイルの測定区間 | 745秒 | 286秒 |
| 1分あたりの完了呼び出し | 42.52回 | 110.98回 |
| プロファイル対象のHTTP所要時間合計 | 717.5秒 | 866.9秒 |
| プロファイル対象の評価項目 | 406回（76.9%） | 402回（76.0%） |
| 確定した往復 | 7件 | 8件 |

並列実行では複数のHTTP要求が重なるため、各要求の所要時間を足した値が実際の経過時間を超えることがあります。4 workersでは要求ごとの競合によってHTTP所要時間の合計が増えましたが、重なって処理できた効果の方が大きく、全体の測定区間は大幅に短くなりました。表の上半分のtoken数と応答数は、同じ要求の再試行と不正な応答も含みます。プロファイル行と処理段階ごとの集計は、保存された `COMPLETE` の一意な呼び出しだけを対象にします。

プロファイルに残った完了呼び出しの差は1回で、約0.2%です。HTTP試行の総数は6回異なります。画像集合と設定ハッシュは同じですが、モデルが進んだ生成・評価経路は完全には一致しませんでした。直列runは `QUALITY_CANDIDATE` 1件、`REJECTED` 5件、`ABSTAINED` 2件です。並列runは `QUALITY_CANDIDATE` 1件、`REJECTED` 4件、`ABSTAINED` 2件、`ERROR` 1件です。したがって、この結果は条件を近づけた2つの運用runの比較であり、まったく同じモデル要求列を1件ずつ比較した結果ではありません。

## 律速となった処理

保存されたプロファイルで最も時間を使ったのは、評価項目ごとのモデル呼び出しです。完了した一意な呼び出しの約76%を両runで占めました。直列runでは406回の呼び出しがあり、プロファイル対象のHTTP所要時間合計は432.1秒です。次に大きかったのは、公開要求の抽出、主張の抽出、質問適合性、画像からのcapability抽出、完全集合の抽出でした。

これより前に50画像runの途中25件を調べたときも、同じ傾向が見つかりました。GPUが動作中でも、vLLMが同時に処理している要求は0件または1件で、待機中の要求は0件でした。コントローラーが多数の小さな評価呼び出しを1件ずつ待つことが主な律速要因です。画像の読み込み、SQLite、最終JSONLの書き込みは、今回のpilot規模では主要因ではありませんでした。

1つの対話内では、前の回答が確定してから次の質問を作る必要があります。この順序は変えられません。一方、ある画像が評価器の応答を待っている間に、別の画像の処理を進められます。画像単位の並列化が有効だったのは、この待ち時間を重ねられたためです。

## エラーと整合性の確認

4 workersのrunでは、不正な構造化応答を2回記録し、1対話が最終的に `ERROR` になりました。評価項目の応答で必須の理由が2回欠けたことが原因で、HTTP通信やGPUメモリの障害ではありません。その後、上限付きの構造化出力再試行を別の8画像で検証しました。途中の不正応答3回から回復し、最終的な `ERROR` は0件でした。この安定性確認は、今回の速度比較には含めていません。

再生検証の結果は次のとおりです。

| run | ハッシュ検証したアーティファクト | モデル呼び出し行 | 確定した往復 |
|---|---:|---:|---:|
| 1 worker | 1,094個 | 528行 | 7件 |
| 4 workers | 1,092個 | 不正応答2回を含む531行 | 8件 |

両データベースでSQLiteの `integrity_check` は `ok`、`foreign_key_check` は0件でした。自動テストでは、複数要求が実際に重なること、出力順、所要時間記録、run storeの書き込みを短時間ずつ直列化することを確認しています。コーディネーターは、設定したworker数までに先行投入を制限します。

どちらの `run` 行も、状態は `CREATED` のままです。この版では、run全体の最終状態を更新していません。そこで、8件の最終対話と再生検証の成功から完了を確認しました。今後runの状態更新を実装すると、進捗を直接判定できます。

## 測定後に加えた改善

コミット `4c43dc9` のフィルタリング見直しでは、適用条件を満たさない評価呼び出しを除きました。別の50画像pilotの最終レコードへ適用すると、少なくとも78回の不要な評価呼び出しを省けます。また、表記をそろえると過去と完全に一致する質問4件は、質問適合性の呼び出し8回より前に停止できます。この8画像による速度比較は再実行していないため、これらの効果を今回の速度向上には含めていません。

評価項目を1つの要求にまとめる方法も、今後の実験候補です。ただし、評価項目ごとに、画像、回答、主張、内部情報のどれを渡せるかが異なります。許可される入力範囲が同じ項目だけをまとめなければ、情報遮断を壊します。また、30,000画像規模では、画像を1件処理するたびに対話JSONL全体を書き直す処理も、改めて計測する必要があります。

## この結果からは分からないこと

- worker数ごとの測定は1回だけで、信頼区間やrun間のばらつきは求めていません。
- 対象は手続き生成画像8件で、Open Imagesは含みません。
- 2つの評価器が同じQwen3.5-9Bを使っているため、standardモデルの性能と評価の多様性は確認できません。
- モデルの読み込みとサーバー起動の時間は含みません。
- 2つのrunでは、最終状態、HTTP試行数、プロファイルに残った完了呼び出し数が完全には一致しません。
- 現在のschemaでは同じ要求の再試行が1行にまとまるため、処理段階ごとの所要時間にはその再試行を含みません。
- 時刻の精度は1秒で、同じ条件での反復測定は行っていません。
- 処理速度の向上だけでは、対話品質を確認できません。目視確認の結果は[Qwen3.5-9B pilot検証レポート](qwen35-9b-pilot_ja.md)に記載しています。

## 再現手順

時間のかかるGPU処理はtmux内で実行します。最初にGPUの利用状況を確認し、[モデルとGPUの手順書](../models-and-gpu_ja.md)に従って `doctor` を実行してください。各runには新しいrun IDと出力先を使います。

```sh
nvidia-smi
tmux new-session -s pixelogue-throughput

uv run --locked pixelogue synthesize \
  --config configs/pilot.yaml \
  --images 8画像を含むマニフェストへのパス.jsonl \
  --artifact-root 準備済み画像ディレクトリへのパス \
  --run-id throughput-serial-YYYYMMDD \
  --output artifacts/throughput-serial/conversations.jsonl \
  --workers 1

uv run --locked pixelogue synthesize \
  --config configs/pilot.yaml \
  --images 8画像を含むマニフェストへのパス.jsonl \
  --artifact-root 準備済み画像ディレクトリへのパス \
  --run-id throughput-parallel-YYYYMMDD \
  --output artifacts/throughput-parallel/conversations.jsonl \
  --workers 4
```

完了後に、機械処理できる性能集計を作り、2つのrun storeを検証します。

```sh
uv run --locked pixelogue profile \
  --database /var/tmp/pixelogue/throughput-serial-YYYYMMDD/run.sqlite3 \
  --output artifacts/throughput-serial/profile.json
uv run --locked pixelogue profile \
  --database /var/tmp/pixelogue/throughput-parallel-YYYYMMDD/run.sqlite3 \
  --output artifacts/throughput-parallel/profile.json

uv run --locked pixelogue replay \
  --config configs/pilot.yaml \
  --run-id throughput-serial-YYYYMMDD
uv run --locked pixelogue replay \
  --config configs/pilot.yaml \
  --run-id throughput-parallel-YYYYMMDD
```

過去の2つのrun IDは再利用しません。各run storeは、元の設定と応答を確認できる記録として保管します。
